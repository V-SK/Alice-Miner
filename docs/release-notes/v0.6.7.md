# Alice Miner v0.6.7 — release notes

> ## Why this one matters
> **Until v0.6.7, a crashed mining engine meant your rig was done for the day —
> and nothing told you.** If the third-party engine (SRBMiner) crashed, or if
> every relay failed in one round, the miner went to `Error` and **stayed there
> forever**: the process still alive, still polling, the GPU idle, and the
> status line silent about it. The only way out was to notice by accident and
> start it again.
> **v0.6.7 makes that impossible.** A crashed or stalled engine now **restarts
> itself automatically**, on a backoff ladder of 5s → 30s → 2m → 5m → 15m →
> 30m that **caps and never gives up**, and the wait is **visible and counting
> down on screen** — with the crash explained in plain language ("heap
> corruption — a fault inside the third-party mining engine, not in Alice").
> **A note on "delete the folder and reinstall":** that never fixed anything.
> The folder was never corrupt — reinstalling just started the process again,
> which is all that was needed. **`stop` then `start` was always enough**, and
> as of v0.6.7 you should not need even that.
> **Every miner should upgrade**, Windows especially. No change to the mining
> lanes, proof-of-possession, rewards, or auto-update. Still a **credit-only
> test build** — see the honesty note at the bottom. `min_supported` stays
> **0.3.0** (older clients get a one-tap auto-update, never a hard block).
>
> ## 这一版为什么重要
> **在 v0.6.7 之前,挖矿引擎一崩,你的机器这一天就废了 —— 而且没有任何东西告诉你。**
> 如果第三方引擎(SRBMiner)崩溃,或者某一轮所有中继都失败,矿工会进入 `Error` 并**永远
> 停在那里**:进程还活着、还在轮询,GPU 却闲着,状态栏对此只字不提。唯一的出路是你碰巧
> 发现,然后手动再启动一次。
> **v0.6.7 让这件事不可能再发生。** 崩溃或停滞的引擎现在会**自动重启**,退避阶梯为
> 5秒 → 30秒 → 2分 → 5分 → 15分 → 30分,**封顶后永不放弃**;等待过程**在界面上可见并
> 逐秒倒计时** —— 崩溃原因也翻译成人话("堆内存损坏 —— 第三方挖矿引擎自身的缺陷,不是
> Alice 的问题")。
> **关于"删掉目录重装"**:它从来没有修好过任何东西。目录从来没有损坏 —— 重装只是把进程
> 重新启动了一次,而那正是唯一需要做的事。**`stop` 再 `start` 一直就够了**;而从 v0.6.7
> 起,你连这个都不该再需要。
> **所有矿工都应升级**,Windows 用户尤其。挖矿 lane、proof-of-possession、奖励、自动更新
> 全部不变。仍是 **credit-only 测试版**(见文末诚实声明)。`min_supported` 保持 **0.3.0**
> (旧客户端一键自动更新,绝不硬块)。

## English

Alice Miner **v0.6.7** is a recovery release over v0.6.6 (`38188a3`). It fixes
one bug with one shape: **"stopped" was permanent.** Two independent paths in
the supervisor could park the miner in a terminal `Error` state from which
nothing — not time, not the watchdog, not the relay coming back — would ever
bring it out.

**1. A crashed engine now restarts itself. Always.**
The client runs a third-party engine (SRBMiner and friends) as a child process.
When that child exited on its own, the supervisor went straight to `Error` and
**returned** — the supervision task ended, so there was no longer anything alive
that could restart it. SRBMiner's heap-corruption abort took exactly this path.
Separately, the Layer-B watchdog had a budget of 3 restarts per 5 minutes and,
once spent, **deliberately gave up**. Either way you were left with a live CLI,
an idle GPU, and a status that had stopped changing.

In v0.6.7 recovery is bounded in **rate**, never in **total**. After the fast
budget is spent, the supervisor keeps retrying on an escalating ladder —
**5s / 30s / 2m / 5m / 15m / 30m, then capped at 30m** — and there is no rung
that means "give up". A self-exit is counted, credited and retried instead of
being terminal. A round where every region failed to relaunch, and a failed
relaunch itself, hand over to the same ladder.

**2. The retry budget is earned by real mining, not by uptime.**
One ladder rung *and* one fast-budget slot are refunded per **10 minutes of
progress-making mining**, where progress is measured from **accepted shares**,
not from how long the process was alive. A rig that mines happily for an hour
and then hits a single crash retries in seconds, not half an hour — the ladder
tracks your *current* health, not your lifetime failure count. Measuring from
shares rather than uptime is deliberate: a wedged engine that stays up forever
while landing nothing must never be able to buy itself retry budget.

**3. The wait is visible, and counts down.**
There is no longer any state that is both `Error` and silent. The retry is armed
under the **same lock** that flips the state, so a crash can never be shown
without its retry, and the status line **refreshes every second**:

> the mining engine crashed: heap corruption — a fault inside the third-party
> mining engine, not in Alice (exit code 0xC0000374) — restarting automatically
> in 5m (attempt 4)

The status carries **machine-readable message keys**, so the desktop app renders
the countdown in whatever language you have selected and re-renders when you
switch. In the GUI a waiting-to-retry state is styled **Warn, not Danger** — it
is a pause, not a failure.

**4. Crash exit codes are translated into plain language.**
An exit code alone tells a miner nothing. v0.6.7 explains the Windows NTSTATUS
aborts an engine actually hits, and marks the ones that are the engine's own
defect **as the engine's own defect**:

| code | meaning |
|---|---|
| `0xC0000374` | heap corruption — *a fault inside the third-party mining engine, not in Alice* |
| `0xC0000005` | invalid memory access — *third-party engine fault* |
| `0xC0000409` | stack buffer overrun — *third-party engine fault* |
| `0xC00000FD` | stack overflow — *third-party engine fault* |
| `0xC0000094` | integer divide by zero — *third-party engine fault* |
| `0xC000001D` | illegal instruction — the engine build may not match this CPU/GPU |
| `0xC0000135` / `0xC0000139` | a required system library is missing — reinstall the engine / the Visual C++ runtime |
| `0xC000013A` / `0x40010005` | terminated by Ctrl-C or a console close |

On macOS and Linux the shell's `128 + signal` convention is decoded the same way
— `134` SIGABRT, `139` SIGSEGV, `137` SIGKILL (*often the OS out-of-memory
killer*), `136` SIGFPE, `132` SIGILL. **A code we cannot explain stays a bare
number.** We do not invent causes.

**5. Restarting cannot stack a second engine on your GPU.**
Restarts pair with the v0.6.6 Windows Job Object: the child handle is **dropped
before any relaunch**, which closes the kill-on-close job and lets the OS take
down the whole old process tree first. Only if teardown *timed out* does the
retry wait on a liveness probe before relaunching — and a child we already
reaped is **never** probed, because a freed pid can be reused and probing it
would risk mistaking an unrelated process for the old engine.

**6. Your Stop still wins. It is the only terminal action.**
A user Stop cancels any pending retry and overrides the ladder. Auto-restart
never fights you.

**7. The "all relays unavailable — restart to retry" line is gone.**
It was telling you to do the one thing the lane now does for itself. Once the
lane retries automatically, that sentence was not merely stale — it was a lie in
the wrong direction, asking for manual work that was no longer required.

**8. `alice-miner start` now names a second running instance.**
Two instances on one machine silently shared a single engine directory, each
overwriting the other's telemetry snapshot, while `stop` could only reach the
one that registered first — so the survivor kept the GPU busy while the UI said
"stopped". `start` now prints a bilingual warning **including the other pid**,
explaining the shared directory, the overwritten telemetry, and the reach of
`stop`. It does not refuse to mine; it turns an afternoon of confusion into one
line.

### Verification
792 workspace tests green on macOS, 784 on Linux, **767 on Windows CI**, with
`clippy --workspace --tests -D warnings` clean on all three. The crash-recovery
tests run on **every OS** — they branch at runtime with `cfg!(windows)` rather
than compiling one arm away with `#[cfg]`, so a Windows report is verified by
Windows, spawning a real crashing child. A unix-only suite for a Windows bug
would have been coverage theatre.

### Thanks
Thanks to the miner on Windows / RTX 4090 who reported this — a rig doing about
145 TH/s with 20,281 cumulative shares that went dark on 2026-08-01 after an
engine heap-corruption abort, and had already been left permanently stalled
after repeated failover on 07-30. The report included the exact state, uptime,
last engine line, and the fact that the GPU had gone idle while the CLI kept
polling; that detail is what made the second, quieter give-up path findable.
A miner that quietly stops earning is the worst kind of bug, because nothing
about it looks like a bug from inside the app.

## 中文

Alice Miner **v0.6.7** 是 v0.6.6(`38188a3`)之上的一个恢复能力版本。它修的是一个只有一种
形状的 bug:**"停止"是永久的。** supervisor 里有两条各自独立的路径,会把矿工停在一个终态
`Error` 上,而此后没有任何东西 —— 时间、看门狗、恢复过来的中继 —— 能把它带出来。

**1. 崩溃的引擎现在会自己重启。永远会。**
客户端会把第三方引擎(SRBMiner 之类)作为子进程运行。当那个子进程自行退出时,supervisor
直接进入 `Error` 并**返回** —— 监督任务就此结束,于是再也没有任何活着的东西能重启它。
SRBMiner 的堆损坏中止走的正是这条路。另外,Layer-B 看门狗有一份"5 分钟内 3 次重启"的预算,
一旦用尽就**主动放弃**。无论走哪条,你留下的都是:一个活着的 CLI、一块闲置的 GPU,以及
一个不再变化的状态。

在 v0.6.7 里,恢复只在**速率**上有界,**总量**上永不设限。快速预算用尽之后,supervisor
会继续沿一条递增阶梯重试 —— **5秒 / 30秒 / 2分 / 5分 / 15分 / 30分,然后封顶在 30 分钟**
—— 阶梯上没有任何一级的含义是"放弃"。子进程自行退出会被计数、记账并重试,而不再是终态。
某一轮所有区域都重启失败、以及重启动作本身失败,都交给同一条阶梯。

**2. 重试预算靠真实挖矿赚回来,而不是靠进程活着。**
每 **10 分钟有进展的挖矿**退还一级阶梯**外加**一个快速预算槽位;"有进展"是按**已接受份额**
衡量的,而不是按进程活了多久。一台机器顺利挖了一小时之后遇到一次崩溃,重试是以秒计而不是
半小时 —— 阶梯跟踪的是你**当前**的健康度,不是你一生的失败次数。用份额而不是运行时长来
衡量是刻意的:一个卡死却永远不退出、什么都挖不出来的引擎,绝不能靠"活着"给自己买到重试预算。

**3. 等待是可见的,而且在倒计时。**
现在不再存在任何"既是 Error 又沉默"的状态。重试是在**翻转状态的同一把锁**下装配的,因此
崩溃不可能在没有重试的情况下被显示出来;状态行**每秒刷新一次**:

> 挖矿引擎崩溃:堆内存损坏(第三方挖矿引擎自身的缺陷,不是 Alice 的问题)(退出码
> 0xC0000374)—— 将在 5m 后自动重启(第 4 次尝试)

状态里带的是**机器可读的消息键**,因此桌面应用会用你当前选择的语言渲染这个倒计时,并在你
切换语言时重新渲染。在 GUI 中,"等待重试"这个状态的样式是 **Warn 而不是 Danger** —— 它是
一次暂停,不是一次失败。

**4. 崩溃退出码被翻译成人话。**
一个孤零零的退出码对矿工毫无意义。v0.6.7 会解释引擎真正会碰到的那些 Windows NTSTATUS
中止码,并把属于引擎自身缺陷的那些**明确标注为引擎自身的缺陷**:

| 退出码 | 含义 |
|---|---|
| `0xC0000374` | 堆内存损坏 —— *第三方挖矿引擎自身的缺陷,不是 Alice 的问题* |
| `0xC0000005` | 非法内存访问 —— *第三方引擎缺陷* |
| `0xC0000409` | 栈缓冲区溢出 —— *第三方引擎缺陷* |
| `0xC00000FD` | 栈溢出 —— *第三方引擎缺陷* |
| `0xC0000094` | 整数除以零 —— *第三方引擎缺陷* |
| `0xC000001D` | 非法指令 —— 该引擎版本可能与此 CPU/GPU 不匹配 |
| `0xC0000135` / `0xC0000139` | 缺少所需的系统库 —— 请重新安装引擎或 Visual C++ 运行库 |
| `0xC000013A` / `0x40010005` | 被 Ctrl-C 或控制台关闭终止 |

在 macOS 与 Linux 上,shell 的 `128 + 信号` 约定也照同样方式解码 —— `134` SIGABRT、
`139` SIGSEGV、`137` SIGKILL(*常见于系统内存不足*)、`136` SIGFPE、`132` SIGILL。
**我们解释不了的退出码,就原样保留为一个裸数字。** 我们不编造原因。

**5. 重启不会在你的 GPU 上叠出第二个引擎。**
重启与 v0.6.6 的 Windows Job Object 配套:子进程句柄会在**任何重启之前被 drop**,这会关闭
那个 kill-on-close 的 job,让操作系统先把旧的整棵进程树带走。只有在拆除**超时**的情况下,
重试才会先等一次存活探测再重启 —— 而对于已经 reap 掉的子进程**绝不探测**,因为释放掉的
pid 可能被复用,探测它反而有把无关进程错认成旧引擎的风险。

**6. 你的"停止"依然说了算。它是唯一的终态动作。**
用户按下的 Stop 会取消任何待执行的重试,并压过整条阶梯。自动重启永远不会跟你对着干。

**7. "所有中继不可用 —— 请重启重试"那句话被删掉了。**
它在叫你去做那件 lane 现在会自己做的事。一旦 lane 会自动重试,那句话就不只是过时 —— 它是
一句方向反了的谎言,在索要一份已经不再需要的手工劳动。

**8. `alice-miner start` 现在会点名第二个正在运行的实例。**
同一台机器上的两个实例过去会悄悄共用同一个引擎目录,各自覆盖对方的遥测快照,而 `stop`
只能够到先注册的那一个 —— 于是活下来的那个继续占着 GPU,界面却显示"已停止"。`start`
现在会打印一条双语警告,**其中包含另一个进程号**,并说明共用目录、遥测互相覆盖、以及
`stop` 能够到的范围。它不会拒绝挖矿;它只是把一下午的困惑变成一行字。

### 验证
macOS 792 项工作区测试全绿,Linux 784 项,**Windows CI 767 项**,三个平台上
`clippy --workspace --tests -D warnings` 均干净。崩溃恢复的测试在**每一个操作系统上**都
运行 —— 它们用运行时的 `cfg!(windows)` 分支,而不是用 `#[cfg]` 把一条分支直接编译掉,
因此一份 Windows 报告是由 Windows 真正启动一个会崩溃的子进程来验证的。为一个 Windows bug
写一套只跑 unix 的测试,那只是覆盖率表演。

感谢那位 Windows / RTX 4090 的矿工提交的报告 —— 一台约 145 TH/s、累计 20,281 份额的机器,

## Honesty note / 诚实声明 (credit-only)

**English.** v0.6.7, like v0.6.0 through v0.6.6, is a **DRY / credit-only test
build**. It really mines and shows your live hashrate and **accepted shares as
credit**, but **`paid_acu = 0` — no real money is paid, no cryptocurrency and no
fiat changes hands, and nothing here is a promise, projection, or guarantee of
earnings, rewards, or returns.** This release is about recovery and honesty —
making a crashed engine come back on its own, making the wait visible instead of
silent, and naming the engine's own defects as the engine's; none of it changes
the fact that this build settles credit only. Automatic restart improves how much
of the time your hardware is actually mining; it does not change what a share is
worth, and the server's ledger remains the sole authority on what you are
credited.

**中文。** v0.6.7 与 v0.6.0 到 v0.6.6 一样,是 **DRY / credit-only 测试版**。它会真实挖矿,
显示实时算力与**以 credit 记账的已接受份额**,但 **`paid_acu = 0` —— 不发放任何真钱,不涉及
任何加密货币或法币,本文档中的任何内容都不构成对收益、奖励或回报的承诺、预测或保证。**
本版本讲的是恢复能力与诚实 —— 让崩溃的引擎自己回来、让等待可见而不是沉默、把引擎自身的
缺陷如实说成是引擎的;这些都不改变本版本只结算 credit 这一事实。自动重启改善的是你的硬件
真正处于挖矿状态的时间占比,它不改变一份份额值多少,服务端账本仍然是你被记账多少的唯一权威。
