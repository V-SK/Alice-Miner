> ## Why this one matters
> **v0.6.8 is about the client telling the truth about failures it does not
> cause.** The headline case is real and recent: a miner whose machine could not
> reach our servers at all was told, in our own words, that *"(address, device) is
> not on the allow-list, so this channel will not earn credit."* That sentence was
> wrong. It sent the miner looking at their account and sent us looking at a relay
> configuration — while the actual problem was an HTTPS connection that never left
> their network. **A client that guesses a cause is worse than a client that says
> it does not know**, and this release removes a whole family of those guesses:
> in the error text, in the AI/training loops that said "waiting for a placement"
> while holding no seat, and in the payout-address check that said "valid" about
> an address the server would refuse.

## English

### 0. The GPU-PRL engine can mine Pearl again — real-hardware verified

*(Lands from `fix/prl-engine-pin-3.5.4-20260814` @ `9e9bb8d`; kept unnumbered so
the sections below keep their numbers. It is the reason this release exists.)*

Pearl hard-forked at height 99000 on **2026-08-11T12:03:43Z** (`SaltedSeedForkHeight`,
CertificateV3 salted seeds). We pinned **SRBMiner-MULTI 3.4.1**, released
2026-06-25 — seven weeks before that spec existed — so from the fork block on,
**every GPU-PRL share this client produced was invalid**. The last accepted share
network-wide is timestamped 12:03:46Z, three seconds after the fork. v0.6.5,
v0.6.6 and v0.6.7 all embed the *identical* engine bytes: no miner could have
escaped this by updating, and there was never a working version to compare
against. **This was our failure, not the miners'.**

v0.6.8 pins **SRBMiner-MULTI 3.5.4** (superset of the vendor's 08-11 emergency
build 3.5.3, which upstream marked MANDATORY).

**Verified on real hardware before shipping** — the step that was missing when
3.4.1 was pinned. On 2026-08-14, 22:51–23:11Z, a rented RTX 3060 in Korea ran a
client **built from the pin branch**, so the client's own resolver fetched the
engine, checked the archive hash *and* the extracted binary hash against the
embedded pin, and only then executed it. Result: **8 accepted shares, 0 rejected,
0 invalid**, at 44.8 TH/s; the relay logged PoP challenge/verify `200` and
upstream login OK with zero rejects; the upstream pool answered `result: true` on
a post-fork job (height 99953, `cert_version: 3`); and the server-side share
ledger recorded exactly those 8 rows — the first entries since the fork second.
Hashes, evidence and endorsement are in `ENGINE-TRUST-LOG.md`, epoch 2.

⚠️ **AMD RDNA2 (RX 6xxx) owners lose the GPU-PRL lane.** SRBMiner removed RDNA2
pearlhash support upstream in 3.5.0. Those cards will not mine *wrongly* — the
lane simply becomes unavailable. There is no version of this fix that keeps them,
and we would rather say so than let you find out from a silent lane.

**That same run caught a second bug, and we fixed it before shipping.** The new
engine also reshaped the two log lines this client reads, so a GPU landing real
accepted shares displayed `0 H/s · 0A/0R · STALL` for the whole twenty minutes —
and the no-progress watchdog restarted a perfectly healthy engine on that false
reading, roughly every ten minutes. Two causes, both now fixed with tests written
from the captured lines: the engine now prints every averaging window on one line,
shortest first, and we were reading the *last* one — the twelve-hour average,
which reads `0.00 H/s` until a rig has run twelve hours; and the share counters
moved out of the old `[719|1|0|…]` bracket into a `key:value` one. Counts are now
taken only from the aggregate `Total:` line, which also fixes a long-standing
multi-GPU bug where a two-card rig's total could flap downwards.

This is worth stating plainly because the acceptance-collapse protection in this
same release reads those two counters: against the new engine it would have seen
no counters at all. It fails safe — a lane it cannot measure is reported as
unknown and is never halted — but the one alarm we added specifically to catch
the August outage would have been blind to it.

The Windows engine binary is **hash-verified only**; it was not executed in the
test above. `[CONFIRM-AT-RELEASE]`

### 1. Error messages that no longer invent a cause

The old text rendered **any** transport-layer failure that mentioned our `/m4/`
route as an allow-list rejection. So a company firewall, an HTTPS-inspecting
router, or an antivirus TLS proxy — none of which our server ever sees — came out
as "your address is not enrolled". Three regions failing at once made it look
even more like an account problem, while the browser on the same machine opened
our website perfectly.

v0.6.8 first answers a narrower, answerable question: **how far did the request
actually get?**

| what we observed | what we now say |
|---|---|
| an HTTP status came back | the server answered — only `401`/`403` may mention the allow-list |
| TLS / certificate failure | the connection was intercepted or its certificate could not be verified; **not** an account problem |
| DNS / connect / timeout | we could not reach the server from this machine |
| a reply we cannot decode | the answer was unreadable — cause unknown |
| none of the above | **we cannot tell** — and it says so, in those words |

A TLS failure now comes with the three checks that actually resolve it: retry on
a phone hotspot, allow `us,asia,eu.aliceprotocol.org` through the security
software, or pin a region with `--region`. `429` is named as rate-limiting, `5xx`
as **our** fault, and any other `4xx` explicitly says it may not be the
allow-list.

The same correction was applied to the supervisor's relay messages. "All relays
unavailable" is a claim about **our** infrastructure that the client cannot
verify; it now reads **"no relay reachable from here"**. (This is exactly the
wording that turned a client-side watchdog bug into a false "region outage"
alarm on 2026-07-25.)

**A correction we owe the record:** the audit that prompted this work said the
client bundles its own root certificates and ignores the OS trust store. That
was true of older builds; **v0.6.7 already reads the system trust store** on all
platforms. So we still do **not** know why that miner's three regions failed
together — a locally-installed inspection CA and a plain TCP/DNS block are both
consistent with the evidence. v0.6.8's job is that the client no longer pretends
to know either.

### 2. AI and training loops that stop claiming to be online

- **Crash loops are now bounded.** A placement that keeps killing its engine used
  to have its failure budget reset by the next poll — the same broken assignment
  could restart forever. The budget now follows a stable fingerprint of the
  placement across polls, and a given-up placement gets a single probe after an
  escalating cooldown, not a fresh budget. Time spent genuinely serving refunds
  budget; a placement that never serves does not.
- **A lost seat is repaired, not narrated.** Losing the seat (or three failed
  heartbeats) now stops the engine and enters an explicit **re-registering**
  state with backoff. Previously the client kept showing "waiting for the center
  to place this stage" while it was no longer in the scheduling pool at all.
- **Readiness is measured on the right port, and says where it came from.** The
  probe used the port from your local config instead of the one the center
  assigned. Head nodes, which are not supposed to listen at all, could sit in
  `launching` forever — or be declared ready because an unrelated program held
  the port. The status line now distinguishes "the engine said it is listening"
  from "a port accepts connections (this is a probe, not the engine's own word)".
- **Unknown protocol answers are no longer filed as "waiting".** Every status
  except `no_assignment` — including a server error envelope — used to render as
  a patient, normal-looking wait. Now anything unrecognised is surfaced as a
  protocol error with a sanitised status and reason code.
- **Incomplete or expiring leases are refused before the GPU starts.** A training
  lease missing its entry point, its held-out commitment, or its expiry used to
  be accepted with empty strings — a full generation spent on a task that could
  not be verified or was already dead. All three are now required and
  format-checked, and the deadline is checked **before generating, before each
  retry, and before submitting**.
- **AI/training child processes join the same process-group / Job Object
  supervision as the mining engines**, so a killed run cannot leave descendants
  holding VRAM and bandwidth.

### 3. Single instance, honest about what it cannot know

Two miners sharing one data directory corrupt each other's bookkeeping. v0.6.8
takes an atomic lock: a second instance **refuses to start** and names the
running pid, the shared directory, and what to do about it — with
`--allow-multiple` as the documented escape hatch.

Two deliberate limits, stated rather than hidden: when the probe **cannot tell**
whether the other process is alive, the miner **starts anyway and says it could
not tell** (refusing on a guess is the same sin this release is about); and a
run started by a service manager **waits** instead of refusing, because launchd
and systemd treat any exit as a reason to relaunch and a refusal would become a
restart storm.

### 4. Self-update rollback now works for headless installs

The health gate that commits a self-update — or rolls back a build that cannot
start — was only ever called by the desktop app. A CLI-only rig that
auto-updated into a broken build **had no rollback at all**. The CLI now arms the
gate as its first action and confirms once the process is demonstrably up.

**`alice-miner --version` no longer counts as a successful start.** It used to:
the confirmation ran the instant the command line was parsed, so printing a
version number committed the update and deleted the last-known-good copy — on a
machine that had not been landing shares recently, that was the *entire*
probation. Printing a version is now recorded as "the binary loads" (which it is,
and which must be recorded, or the *second* `--version` would look like a
crash-on-launch and trigger a rollback) while the commit waits for a command you
actually asked for.

Two honest limits remain. This still proves the binary **starts**, not that it
mines; and on a machine whose previous build was **not** landing accepted shares
in the last 72 h there is no earning baseline to judge the new one against, so
the mining half of the probation abstains and `alice-miner start` commits on the
start proof alone. A build that starts cleanly and dies the moment it mines, on
such a machine, still has no automatic rollback. Fixing that means holding a
spare copy of the app until the probation times out; it is a deliberate open item,
not an oversight.

### 5. Payout address: checked properly, and confirmed by a human

The client used to check only the shape of your `prl1p…` return address — it
said so in its own source — and then signed an enrollment for it. A single
mistyped character was signed, sent, and rejected server-side; you found out from
a rebate that never arrived.

v0.6.8 verifies the **full bech32m checksum and the witness program** — the same
rule the server's payout boundary applies — **before anything is signed**, and
shows you the **complete, unmasked address** to confirm. It never infers consent
from silence: non-interactive use requires an explicit flag.

Behaviour changes worth knowing: `identity --set-prl-payout` refuses without
`--confirm-payout` when there is no terminal or `--json` is set; `setup
--prl-payout` needs `--yes` non-interactively; and an address already stored (or
set via env) that fails the checksum is now reported as an error everywhere
instead of being used silently.

### 6. Hostile text cannot repaint your terminal

Remote strings — model ids, roles, reason codes, HTTP error bodies — went
straight to the CLI. ANSI/OSC escapes in them can forge a success line, hide a
warning, or redraw the screen. They are now sanitised where they enter **and**
where they are printed. Model **prompts are deliberately not sanitised** (they
are program input, not display text) and tests pin that distinction.

The update button's download URL from the read API is now restricted to
`github.com` over HTTPS; anything else falls back to the built-in official
releases page.

### 7. Groundwork for encrypted mining connections

The GPU-PRL and alpha lanes ignored an endpoint declared `transport: tls` and
mined in the clear anyway. They now consume the transport field like the XMR and
RVN lanes: PRL emits `stratum+ssl://` for a TLS endpoint, and the alpha lane —
whose real engine takes a bare `host:port` with no verified TLS syntax —
**refuses** a TLS endpoint rather than silently mining in the clear.

**This changes nothing on the live network today.** Every endpoint is plaintext,
the generated command line is byte-for-byte identical to v0.6.7, and **our
relays do not terminate TLS yet** — the client half is simply ready for the day
they do.

### 8. The mining engine's pin can be updated without a client release

On 2026-08-11 Pearl hard-forked its algorithm. SRBMiner-MULTI 3.5.3 shipped that
morning marked MANDATORY; our client pinned 3.4.1 by SHA-256, compiled into the
binary. From 12:04Z every share was rejected upstream, for days. **Self-update
could not have fixed it**: v0.6.5, v0.6.6 and v0.6.7 pin the *identical* engine
bytes, so a miner on the newest client was rejected exactly as hard as one on the
oldest.

v0.6.8 keeps the engine machinery unchanged — download, verify against a pin,
install atomically, never exec bytes that do not match — and moves the **pin
table** onto its own signed document (`engines.json`, signed with a **separate
engine-pin sub-key**, not the release root key). The pins compiled into the
client become a floor rather than the only source.

* Refuses the whole document — and keeps the built-in pins — on a bad signature,
  an unknown schema, an unsafe entry, a URL outside the upstream release hosts
  compiled into the client, a replayed/rolled-back epoch, or a re-issue of a
  version we have already trusted with different bytes.
* A new pin becomes effective only **after** the engine it names is downloaded and
  hashed to match. A hash mismatch refuses the document; a network failure defers
  it. Either way the current engine keeps mining — and an engine that fails
  verification stops its lane rather than falling back to older bytes.
* `alice-miner engines` shows the pinned SHA-256, upstream version + release URL,
  endorsement date, whether the pin is built in or from a signed list, and whether
  those bytes are present and verified here. `--check` pulls a new pin now.
* Endorsing an engine build stays a human decision, recorded in
  `ENGINE-TRUST-LOG.md` and signed offline by hand.

**The pin carries the CALL, not just the bytes.** A pin that only names bytes is
not enough, and we found that out the same week: SRBMiner-MULTI 3.5.4 reshaped
both log lines the client's parser reads, so during the 2026-08-14 verification
run a healthy GPU landing accepted shares at 44.8 TH/s displayed
`0 H/s · 0A/0R · STALL` and the no-progress watchdog restarted it on that false
reading. The parser is fixed — but no published `engines.json` could have fixed
it, which is the opposite of what this feature promises. So a signed entry may
now also carry the **algorithm token**, **extra argv**, and **which of the
client's log parsers** reads the engine's output. All three are optional (absent
⇒ byte-for-byte the old behaviour), all three are bounded, and all three are
fail-closed: an unknown parser id, a flag-shaped algorithm token, or an extra
argument that restates a flag the client owns (the pool, your login, the
password, the log file, device selection) refuses the whole document.

**Engine versions only go forward.** Nothing previously stopped a signed pin
pointing back at an *older* upstream build that is still hosted — SRBMiner 3.4.1
after the fork, say, which is a one-key replay of the outage this release exists
for. The client now remembers the highest version it has ever run for each engine
and refuses a backwards step, including a version string it cannot confidently
order (`3.5.4-rc1` vs `3.5.4` is refused, not guessed). A deliberate downgrade is
still possible — sometimes it is right — but it must be declared in the document
with a reason, and that reason is shown to you by `alice-miner engines` and
flagged by `alice-miner doctor`.

**Honest limits:** *this* fork still needs one client release — the one that
carries the sub-key. After that, a client release is still required for a fork
whose output needs a **parser we do not compile in**, one that renames the flags
the client owns, or one hosted somewhere outside the upstream release pages
compiled into the client. Everything else — new version, new bytes, renamed
algorithm, an added switch — is a published document away. And the pin proves
integrity, not provenance: if the upstream vendor's own account were compromised,
the pin would distribute that build faithfully to the whole fleet. That risk is
written up, and accepted rather than mitigated, in `ENGINE-TRUST-LOG.md`.
`[CONFIRM-AT-RELEASE]`

### 9. Updates that can install themselves — with the brakes built first

Until now the client updated **only** when someone typed a command or clicked a
button. That is slow, and in August 2026 slow cost a miner three days of
electricity. So v0.6.8 can install a signed update on its own — and every part of
that sentence is fenced, because automatic installation is the single most
dangerous capability a client can have. If our release key were ever stolen, an
attacker could sign a malicious build, and automatic installation is what turns
that from a problem into remote code execution on every mining machine. Rotating
the key afterwards does not un-install anything.

So the brakes came first, and they are enforced **by the client**, not by the
manifest we publish:

* **A day of daylight.** A version must have been visible to *your* machine for
  24 hours before it installs itself. The clock is local: it starts when your
  client first sees the version, not from any date in the release. A published
  release cannot shorten it — the field exists, and it can only ask for *longer*.
* **In batches.** A release names a percentage; your machine falls into a stable
  bucket, so a bad build reaches a slice of the fleet and not all of it. The
  bucket is drawn from a random local label that is never sent anywhere and is
  not derived from your hardware or your address.
* **The same version can never change its bytes.** Your client remembers the
  package hash it first saw for each version. If the same version number ever
  shows up with different bytes, it refuses, downloads nothing, and says so.
  This is the one check with no override anywhere, so the one case where it
  *cannot* run is worth stating: if that local record is ever unreadable, the
  client says so, holds the automatic install, keeps the damaged file as
  `update-seen.json.unreadable`, and starts the record — and that version's
  24-hour clock — again from scratch. It does not quietly rebuild the record and
  report that everything checked out, which is what it used to do.
* **It installs once.** An update does not replace the program you are running;
  it takes effect at your next start, which on a rig can be days away. The client
  now records what it installed, so the next check says "already installed,
  restart when convenient" instead of installing it again — which would have
  overwritten the very copy it keeps in order to roll back.
* **A kill switch that works on clients already out there.** A release can be
  **withdrawn**. A withdrawn version is never installed — not automatically, and
  not by `alice-miner update --yes` either — and a machine already running one is
  told, and reverted to its previous build where it is allowed to act.
* **It has to still work.** A build that installs itself is on probation: if it
  fails to start twice, it is rolled back and never auto-installed on that
  machine again. And if it starts but stops landing accepted shares — on a
  machine that *was* landing them before the update — it is rolled back too.
  Crucially, that second test is **switched off when the previous build was not
  earning either**, because that is what an upstream outage looks like, and
  blaming the client for the network is the exact mistake this whole release is
  about.

**The default is `security-only`:** releases we explicitly mark as security fixes
install themselves; everything else only tells you it exists. Choose differently
with `alice-miner update --auto off|notify|security-only|full`, or in Settings →
Software update. `off` means off — no check, no network, nothing.

Two things we will not pretend. First, none of the above stops a stolen release
key; it shortens the window in which one reaches everybody from "however long
until people update by hand" to about a day, and gives us a revocation switch to
use inside that day. The real fix is two-person signing, and it is not built yet.
Second, **automatic client updates would not have fixed the August 2026 outage
at all** — v0.6.5, v0.6.6 and v0.6.7 all pin the same mining engine, so a miner
on the newest client was rejected exactly as hard as one on the oldest. That
failure needs the engine pin to be updatable on its own — which is section 8 of
this same release.

Mining is never interrupted for an update: a new build is swapped in on disk and
takes effect the next time you start.

### 10. macOS: a `.dmg`, a packaging gate, and honest install docs

A miner on macOS arm64 could not launch v0.6.7: Finder error `-47`, then
`-10827 kLSNoExecutableErr` ("the executable is missing") from `open` even after
clearing quarantine. We rebuilt the shipped artifact and checked it. **The v0.6.7
zip is not damaged** — it round-trips through `ditto` with `0755` intact,
`codesign --verify --deep --strict` passes on the extracted copy, every nested
Mach-O (`xmrig`, `alice-miner-cli`) is individually signed, and the bundled
engine still matches its `miners.json` pin. Nothing about the packaging changed
between v0.6.6 and v0.6.7.

What is actually wrong is older and larger than any one release: **the app is
ad-hoc signed and not notarized, because Alice has no paid Apple Developer ID.**
Gatekeeper refuses it on every Mac, and no change to how we archive it can alter
that. We are saying so plainly in the docs now instead of leaving people to
rediscover it.

What this release does do:

- **Ships `AliceMiner-macos-arm64.dmg`** beside the zip. The zip is fine as an
  archive; what it cannot do is stop people double-clicking the app inside
  `~/Downloads`, where a quarantined bundle is App-Translocated onto a randomised
  read-only mount — the real cause of "it opens and does nothing", settings that
  never persist, and self-update failures. A DMG makes the drag to
  `/Applications` the obvious gesture, and that drag is what ends translocation.
  The zip is still published and still drives the in-app updater.
- **Adds a release-time gate** (`scripts/verify_macos_bundle.sh`) that unpacks
  the artifact we just built and refuses to ship it unless a Mac could launch it:
  `Contents/MacOS/<CFBundleExecutable>` exists under the name `Info.plist`
  promises (the literal `-10827` condition), the exec bit survived, the signature
  still verifies after the archive round trip **and** under quarantine, every
  nested Mach-O is signed, and the engine SHA-256 pins still hold. It runs in CI
  and in `scripts/release.sh`. It reports the ad-hoc/unnotarized status loudly but
  does not fail on it — that only becomes an error once a Developer ID exists.
- **Rewrites the macOS docs** with what the two error codes actually mean, why
  `right-click → Open` has been dead since macOS 15 Sequoia, why
  `com.apple.provenance` surviving quarantine removal is harmless, and how to
  reset a stale LaunchServices record. EN + ZH.

**This does not make the app open cleanly for a normal user.** Downloading with a
browser and double-clicking still hits Gatekeeper, and still needs Privacy &
Security → Open Anyway or a manual `xattr -dr`. The only complete fix is an Apple
Developer ID certificate (99 USD/year) plus notarization in the release pipeline.
`[CONFIRM-AT-RELEASE]`

### 11. A stopped lane now stays stopped across a reboot — and unstops itself

When the pool accepts essentially nothing, this client stops mining rather than burn power for
results nobody will credit. That protection existed before; it just could not survive anything.

It is now written to disk with its evidence, so a restart no longer silently clears it and burns
another window. That matters most on the machines least likely to be watched: a headless rig under
a service manager was the population that burned three days in August, and it is the population a
supervisor restarts most often.

Because a stop that only a human can lift would be its own outage, the client now lifts it by
itself on a bounded ladder — about 30 minutes, then an hour, two, four, capped at six. Each attempt
costs one window of electricity, which is the deliberate price of the network being able to come
back without every miner having to touch their rig. Only a **measured** healthy period retires it;
an uptime, a reconnect or a restart is not evidence.

**What changes for you:** a rig running as a background service that stops for this reason will now
still be stopped after a reboot, until its next scheduled re-check. Pressing Start, or running
`alice-miner start` yourself, clears it immediately — a person's rig is a person's call, and only
starts that came from a service manager honour the stored stop.

### 12. The CPU engine donates 1%, and we cannot turn it off

We pass `--donate-level 0` to the bundled xmrig. It reports `DONATE 1%` regardless: official xmrig
enforces a one percent minimum, and we verified this against the exact binary this release ships.

So roughly 1% of a CPU miner's hashing goes to xmrig's author rather than to our relay — and
therefore does not become ALICE credit. It is small, it is not new, and it is not something we can
change from our side without replacing the engine. We are stating it because you should hear it
from us rather than from a banner line in the engine's own log.

The GPU engines are unaffected.

v0.6.8 改钉 **SRBMiner-MULTI 3.5.4**(厂商 08-11 紧急版 3.5.3 的超集,上游标注

⚠️ **AMD RDNA2(RX 6xxx)将失去 GPU-PRL lane。** SRBMiner 从 3.5.0 起在上游移除了

**同一次真机跑,还抓出了第二个 bug,发版前已修。** 新引擎同时改了本客户端要读的两行日志,
于是一台**正在真的出有效份额**的显卡,面板整整二十分钟显示 `0 H/s · 0A/0R · STALL`;而
"无进展"看门狗就按这个假读数,大约每十分钟重启一次一台完全健康的引擎。两个原因都已修好,
测试直接用真机抓下来的原文行:一是引擎现在把所有平均窗口打印在同一行、最短的在最前,而我们
读的是**最后一个**——十二小时平均值,矿机跑满十二小时之前它一直是 `0.00 H/s`;二是份额计数
从原来的 `[719|1|0|…]` 括号搬进了 `key:value` 括号。现在计数只从汇总的 `Total:` 行取,
这顺带修掉了一个长期存在的多卡 bug:双卡矿机的总数原本可能往下跳。

这件事值得明说,因为本版新增的"接受率崩塌保护"读的正是这两个计数器:面对新引擎,它会**一个
计数都读不到**。它是 fail-safe 的——测不出来的通道会如实报"未知"、绝不停机——但我们专门
为这次事故加的那道警报,本来会对它全程失明。

### 1. 不再编造原因的错误信息

旧文案把**任何**提到 `/m4/` 的传输层失败都渲染成"未进入允许名单"。于是公司防火墙、
做 HTTPS 中间人的路由器、杀毒软件的 TLS 扫描 —— 这些我方服务器**根本看不到**的东西 ——
统统被说成"你的地址没有注册"。三个区域同时失败让它看起来更像账户问题,而同一台机器上
的浏览器打开我们网站却毫无问题。

v0.6.8 先回答一个更窄、但**能够回答**的问题:**这个请求到底走到了哪一层?**

| 我们观测到什么 | 现在怎么说 |
|---|---|
| 收到了 HTTP 状态码 | 服务器答复了 —— 只有 `401`/`403` 才允许提"允许名单" |
| TLS / 证书失败 | 连接被拦截或证书无法验证;**不是**账户问题 |
| DNS / 连接 / 超时 | 本机联系不上服务器 |
| 收到了但读不懂 | 答复无法解析 —— 原因未知 |
| 以上都不是 | **分不清** —— 就照这四个字说 |

TLS 失败现在附带三条真正管用的自查:换手机热点重试、在安全软件里放行
`us,asia,eu.aliceprotocol.org`、用 `--region` 指定区域。`429` 明说是限流,`5xx` 明说
是**我方**故障,其它 `4xx` 明确写出"不一定是允许名单"。

同样的修正应用到了监督器的中继文案。"所有中继不可用"是一个关于**我方基础设施**的断言,
而客户端根本无从验证;现在改为**"本机联系不上任何区域中继"**。(2026-07-25 那次把
客户端看门狗 bug 误报成"区域故障"的假警报,用的正是旧措辞。)

**一条必须记录在案的更正:** 触发这项工作的审计说客户端自带根证书、不读系统证书库。
这对更早的版本成立,但 **v0.6.7 已经在所有平台读系统证书库**。所以那位矿工三区同挂的
真正原因**我们仍然不知道** —— 本机安装的拦截 CA、以及纯 TCP/DNS 封锁,都与现有证据
相符。v0.6.8 要做的,是让客户端不再假装自己知道。

### 2. 不再谎称"在线"的 AI 与训练循环

- **崩溃循环现在有界。** 一个不断把引擎搞崩的分配,过去会在下一次轮询时被当成全新分配
  而把失败预算清零 —— 同一个坏分配可以永远重启下去。现在预算跟着分配的稳定指纹跨轮询
  存活;已放弃的分配在递增冷却后只得到**一次探针**,而不是一整份新预算。真正在服务的
  时长会退还预算,从不服务的分配则不会。
- **座位丢了要去修,而不是拿话搪塞。** 座位丢失(或连续三次心跳失败)现在会**停引擎**、
  进入显式的**重新注册**状态并带退避。此前客户端会一直显示"等待调度中心分配此阶段",
  而它其实早已不在调度池里。
- **就绪判定改用正确的端口,并说明结论从哪来。** 探测用的是你本地配置的端口,而不是
  中心分配的端口。按设计不监听的 head 节点可能永远停在 `launching`,也可能因为一个
  无关程序占了端口而被判成 ready。状态行现在区分"引擎已报告正在监听"与"端口可接受连接
  (这是探测结果,并非引擎自述)"。
- **读不懂的协议答复不再归档为"等待"。** 除 `no_assignment` 外的所有状态 —— 包括服务端
  错误信封 —— 过去都渲染成一个安静正常的等待。现在任何无法识别的状态都作为协议错误
  暴露出来,并附经过清洗的状态与 reason code。
- **不完整或即将过期的租约,在 GPU 开工前就被拒。** 缺 entry point、缺 held-out 承诺、
  缺过期时间的训练租约,过去会被接受并填空串 —— 一次完整生成花在一个无法验证、或早已
  失效的任务上。现在这三个字段必填且格式校验,并在**生成前、每次重试前、提交前**三处
  检查截止时间。
- **AI/训练子进程纳入与挖矿引擎相同的进程组 / Job Object 管理**,被杀的运行不会再留下
  占着显存和带宽的后代进程。

### 3. 单实例,并且对"查不出的事"诚实

两个矿工共用一个数据目录会互相破坏账目。v0.6.8 采用原子锁:第二个实例**拒绝启动**,
并报出正在运行的 pid、共用的目录、以及可以怎么办 —— `--allow-multiple` 是写明的逃生口。

两处刻意的限制,说出来而不是藏起来:当探测**查不出**对方进程是否活着时,矿工**照常启动
并明说自己查不出**(靠猜来拒绝,正是本版本要清除的那种毛病);由服务管理器拉起的运行则
**等待**而不是拒绝,因为 launchd 和 systemd 把任何退出都当成重新拉起的理由,拒绝会变成
重启风暴。

### 4. 无界面安装现在也能回滚自更新

那道"确认自更新 / 回滚起不来的构建"的健康门,一直以来只有桌面应用会调用。纯 CLI 的矿机
自动更新到一个坏构建后**完全没有回滚**。现在 CLI 在最早的位置武装这道门,并在进程确实
起来后确认。

**`alice-miner --version` 不再算作一次"成功启动"。** 过去算:确认动作在命令行解析完的
那一刻就执行,于是"打印一个版本号"就提交了更新、删掉了最后已知可用副本 —— 而在一台近期
没有产出份额的机器上,那**就是全部**观察期。现在打印版本号只被记为"这个二进制能加载"
(它确实能,而且必须记下来,否则**第二次** `--version` 会被误判成启动即崩而触发回滚),
提交则要等到一条你真正要求执行的命令。

两处诚实的边界仍然存在:它证明的是这个二进制**能启动**,不是它能挖矿;并且当这台机器
上**上一个版本近 72 小时也没有被接受的份额**时,没有可对照的收益基线,观察期的挖矿那一半
会弃权,`alice-miner start` 只凭"启动成功"就提交。因此在这种机器上,一个能正常启动、
一开挖就死的构建,仍然没有自动回滚。要修它就得把备份副本一直留到观察期超时 —— 这是一个
**刻意留下的待办**,不是疏漏。

### 5. 返还地址:真校验,并且由人确认

客户端过去只检查 `prl1p…` 返还地址的**形状** —— 源码里自己写明了这一点 —— 然后就为它
签名注册。打错一个字符照签照发,由服务端拒绝;而你是从"返还一直没到"才知道的。

v0.6.8 在**签名之前**验证**完整的 bech32m 校验和与 witness 程序** —— 与服务端付款边界
所用的是同一条规则 —— 并把**完整、不打码的地址**显示给你确认。它绝不从沉默推断同意:
非交互使用必须带显式 flag。

需要知道的行为变化:无终端或带 `--json` 时,`identity --set-prl-payout` 不带
`--confirm-payout` 会被拒绝;`setup --prl-payout` 非交互需要 `--yes`;已经存好(或从环境
变量读入)但校验和错误的地址,现在处处报错,而不是被静默使用。

### 6. 恶意文本无法重绘你的终端

远端字符串 —— model id、role、reason code、HTTP 错误正文 —— 过去直接进 CLI 输出。其中的
ANSI/OSC 转义可以伪造一行成功、隐藏一条警告、或者整屏重绘。现在它们在**进入时**和
**打印时**各清洗一次。模型 **prompt 刻意不清洗**(它是程序输入,不是显示文本),并有测试
钉死这条区分。

更新按钮从 read API 拿到的下载地址,现在被限制为 HTTPS 的 `github.com`;其它一律回退到
内置的官方 releases 页。

### 7. 为加密挖矿连接铺路

GPU-PRL 与 alpha lane 过去会忽略端点上声明的 `transport: tls`,照样明文挖。现在它们像
XMR / RVN lane 一样真正消费 transport 字段:PRL 对 TLS 端点输出 `stratum+ssl://`;
而 alpha lane —— 其真实引擎接受的是裸 `host:port`、我们**从未验证过它的 TLS 语法** ——
对 TLS 端点选择**拒绝**,而不是嘴上 tls、手上明文。

**这在今天的线上网络零变化。** 所有端点都是明文,生成的命令行与 v0.6.7 逐字节相同,
而且**我方中继目前还没有 TLS 端**可连 —— 客户端这一半只是先就位。

### 8. 引擎 pin 可以独立于客户端发版更新

2026-08-11 Pearl 硬分叉换算法。SRBMiner-MULTI 3.5.3 当天上午发布并标注 MANDATORY;
我方客户端把 3.4.1 的 SHA-256 编译进了二进制。从 12:04Z 起,所有份额被上游判无效,
持续数天。**自动更新救不了这次**:v0.6.5 / v0.6.6 / v0.6.7 pin 的是**同一份**引擎字节,
升到最新客户端的矿工,被拒得和用最老版本的一模一样。

v0.6.8 不动引擎机制本身 —— 下载、对 pin 校验、原子安装、校验不过绝不运行 —— 只把
**pin 表**搬到一份独立签名的文件(`engines.json`,用**独立的 engine-pin 子钥**签名,
不是发布根钥)。编译进客户端的 pin 从"唯一来源"变成"下限(floor)"。

* 验签失败、schema 不认识、条目不安全、URL 不在客户端内置的上游发布域、epoch 回放或
  回退、把已信任的版本换成另一份字节 —— 任一情况**整份拒收**,继续用内置 pin。
* 新 pin 只有在它指向的引擎**下载并哈希校验通过之后**才生效。哈希不符=拒收整份清单;
  网络失败=推迟重试。两种情况下当前引擎都继续挖 —— 而校验不过的引擎会**停掉该通道**,
  绝不回退到旧字节继续跑。
* `alice-miner engines` 显示固定的 SHA-256、上游版本与发布页 URL、背书时间、pin 来自
  内置表还是签名清单(及其 epoch)、以及这些字节在本机是否已安装并校验通过;`--check`
  可立即拉取新 pin。
* 背书哪个引擎版本仍是**人的决定**,记录在 `ENGINE-TRUST-LOG.md`,并由 V 离线亲手签名。

**pin 带的不只是字节,还有"怎么调用"。** 只钉字节是不够的,而我们在同一周就撞上了:
SRBMiner-MULTI 3.5.4 改写了客户端解析器依赖的那两行日志,于是 2026-08-14 那次验证运行中,
一块健康的 GPU 以 44.8 TH/s 拿到被接受的份额,面板却显示 `0 H/s · 0A/0R · STALL`,
无进展看门狗还照着这个假读数重启了引擎。解析器已修 —— 但**再怎么发 `engines.json` 都修不了
这件事**,这恰恰与本功能的承诺相反。所以签名条目现在还可以携带**算法 token**、
**附加 argv**、以及**用客户端的哪一个日志解析器**读它的输出。三者都是可选的(不填 ⇒
与旧行为逐字节相同)、都有上限、且都**fail-closed**:不认识的 parser id、长得像 flag 的
算法 token、或一个重述了客户端自有 flag(矿池、你的登录、密码、日志文件、显卡选择)的
附加参数,都会导致**整份文档被拒**。

**引擎版本只能向前。** 过去没有任何东西阻止一份签名 pin 指回上游仍在托管的**更旧**版本 ——
比如分叉后指回 SRBMiner 3.4.1,那就是用一把钥匙重放本版本存在的理由。现在客户端会记住
每个引擎它运行过的最高版本,并拒绝任何回退,包括它**无法有把握排序**的版本串
(`3.5.4-rc1` 与 `3.5.4` 之间会被拒绝,而不是猜)。有意降级仍然可以 —— 有时它就是对的 ——
但必须在文档里声明并写明理由,而这条理由会由 `alice-miner engines` 显示给你、并由
`alice-miner doctor` 标出。

**诚实的边界:**这一次分叉仍然必须先发一版客户端(带上子钥的那一版)。在那之后,以下
情况**仍然需要发客户端**:分叉的输出需要一个**我们没有编译进去的解析器**、上游改掉了
客户端自有的那些 flag、或者引擎搬到了客户端内置上游发布域之外。其余情况 —— 新版本、
新字节、改名的算法、新增一个开关 —— 发一份文档即可。另外,pin 保证的是**完整性,不是
来源真实性**:如果上游厂商自己的账号被攻陷,pin 会把那份构建**忠实地**分发给全舰队。
这条风险写在 `ENGINE-TRUST-LOG.md` 里,是**被接受**而非被缓解的。`[CONFIRM-AT-RELEASE]`

### 9. 可以自己安装的更新 —— 但刹车先装好

在此之前,客户端**只有**在有人敲命令或点按钮时才更新。这很慢,而 2026 年 8 月,慢让
一位矿工白烧了三天电。所以 v0.6.8 可以自行安装已签名的更新 —— 而这句话的每一部分都
被围了栏,因为**自动安装是一个客户端能拥有的最危险的能力**。如果我们的发布密钥被盗,
攻击者就能签出恶意版本,而自动安装会把这件事从"一个问题"变成"每一台矿机上的远程
代码执行"。事后轮换密钥,并不能把已经装上的东西卸下来。

所以刹车先装,而且由**客户端**强制执行,不由我们发布的清单决定:

* **晾一天。** 一个版本必须在**你这台机器**上被看见满 24 小时,才可能自行安装。这个
  时钟是本地的:从你的客户端第一次看到该版本开始算,而不是从发布日期算。发布清单
  **无法缩短它** —— 那个字段存在,但只能要求**更长**。
* **分批放量。** 一次发布会写明百分比;你的机器落在一个稳定的分组里,于是坏版本只会
  触达舰队的一部分,而不是全部。分组来自一个**随机的本地标签**,它从不上传,也不由
  你的硬件或地址推导而来。
* **同一个版本号,字节永远不能变。** 客户端会记住每个版本首次见到的安装包哈希。如果
  同一个版本号后来带着不同的字节出现,它会拒绝、不下载任何东西,并把这件事说出来。
* **对已经装出去的客户端也生效的紧急开关。** 一次发布可以被**撤回**。被撤回的版本永远
  不会被安装 —— 自动不会,`alice-miner update --yes` 也不会 —— 而已经在运行该版本的
  机器会被告知,并在其设置允许自动动作时回退到上一个版本。
* **装上之后还得能用。** 自行安装的版本处于**观察期**:两次启动失败就回滚,并且此后
  再也不会在这台机器上自动安装。若它能启动、却不再有被接受的份额 —— 而这台机器在更新
  **之前是有的** —— 同样回滚。关键在于:当**上一个版本也同样没有收益**时,第二项检测
  **自动关闭**,因为那正是上游故障的样子;把网络的问题算到客户端头上,恰恰是本次发布
  从头到尾想要纠正的那个错误。

**默认值是 `security-only`:** 我们明确标记为安全修复的版本会自行安装,其余版本只提示。
用 `alice-miner update --auto off|notify|security-only|full` 修改,或在"设置 → 软件更新"
里选。`off` 就是彻底关闭 —— 不检查、不联网、什么都不做。

有两件事我们不会假装。第一,上面这些**挡不住被盗的发布密钥**;它只是把"被盗密钥触达
所有人"的窗口,从"等大家自己手动更新的那么久"压缩到大约一天,并让我们在这一天里有一个
撤回开关可用。真正的根治是**双人签名**,它还没有做。第二,**自动客户端更新根本解决不了
2026 年 8 月那次事故** —— v0.6.5、v0.6.6、v0.6.7 pin 的是同一个挖矿引擎,用最新客户端的
矿工被拒得和用最旧客户端的一模一样。那次故障需要的是"引擎 pin 能独立更新" —— 那正是本版第 8 节。

更新永远不会打断挖矿:新版本在磁盘上就位,下次启动时生效。

### 10. macOS:发 `.dmg`、加打包关卡、把安装文档说实话

有矿工在 macOS arm64 上打不开 v0.6.7:访达报 `-47`,清掉隔离标记后 `open` 又报
`-10827 kLSNoExecutableErr`(「可执行文件缺失」)。我们把线上发的那个产物取回来重验了一遍:
**v0.6.7 的 zip 没有坏** —— 经 `ditto` 往返后 `0755` 权限位完好,解压出来的包
`codesign --verify --deep --strict` 通过,包内每个 Mach-O(`xmrig`、`alice-miner-cli`)
都各自签了名,自带引擎的哈希仍与 `miners.json` 的钉子一致。v0.6.6 到 v0.6.7 之间打包流程
一个字都没改。

真正的问题比任何一个版本都更老、更大:**这个 App 是 ad-hoc 签名、未经公证,因为 Alice
没有付费的 Apple Developer ID。** Gatekeeper 在每一台 Mac 上都会拦它,我们怎么打包都改不了
这一点。现在我们把这句话直接写进文档,而不是让每个人自己撞一遍才发现。

这一版实际做了:

- **在 zip 之外增发 `AliceMiner-macos-arm64.dmg`。** zip 作为压缩包本身没问题,但它挡不住
  用户直接在 `~/下载` 里双击 App —— 带隔离标记的包会被 App Translocation 丢到一个随机只读
  挂载点上运行,这才是「点了没反应」「设置每次都丢」和自更新失败的真因。DMG 让「拖进
  `/Applications`」成为唯一自然的动作,而这个拖拽正是解除 translocation 的条件。zip 继续
  发布,App 内自动更新仍走 zip。
- **加了一道发版关卡**(`scripts/verify_macos_bundle.sh`):把刚打好的产物重新解开,确认一台
  Mac 真的能启动它,否则拒绝发布 —— `Contents/MacOS/<CFBundleExecutable>` 必须以
  `Info.plist` 承诺的那个名字存在(这正是 `-10827` 的字面条件)、可执行位必须还在、签名在
  压缩往返后**以及**在带隔离标记时都必须仍然验得过、每个内嵌 Mach-O 都必须已签名、引擎
  SHA-256 必须仍等于钉子。CI 与 `scripts/release.sh` 都会跑。它会大声报告 ad-hoc / 未公证
  这一事实,但不因此判失败 —— 那要等真的拿到 Developer ID 之后才升级为硬错误。
- **重写 macOS 文档**:两个错误码到底是什么意思、为什么「右键 → 打开」自 macOS 15 Sequoia
  起已经失效、为什么清完隔离标记后 `com.apple.provenance` 还在是无害的、以及怎么重置陈旧的
  LaunchServices 记录。中英文同步。

**这并不能让普通用户第一次双击就打开。** 用浏览器下载再双击,仍然会被 Gatekeeper 拦,仍然
需要「隐私与安全性 → 仍要打开」或手动 `xattr -dr`。唯一的完整解法是买 Apple Developer ID
证书(99 美元/年)并在发布流程里加上公证(notarization)。`[CONFIRM-AT-RELEASE]`

### 11. 停下的通道现在能跨重启保持停止 —— 也能自己重新开始

当矿池几乎什么都不接受时,这个客户端会停止挖矿,而不是继续为没人计分的结果烧电。这个保护之前就有,
只是它撑不过任何事情。

现在它会带着证据落盘,所以重启不再会悄悄清掉它、再烧掉一整个窗口。这一点对最没人盯着的机器最要紧:
以后台服务方式运行的无人值守矿机,正是 8 月烧了三天电的那一群,也正是最经常被服务管理器重启的那一群。

而一个只有人才能解除的停止本身就是一次停摆,所以客户端现在会自己按一个有上限的阶梯重新试:大约 30
分钟,然后 1 小时、2 小时、4 小时,封顶 6 小时。每次尝试都要花掉一个窗口的电——这是"整个网络不需要
每个矿工亲自动手就能恢复"的明码标价。只有**真正测量到的**健康周期才能让它退休;开机时长、重连、重启
都不算证据。

**对你意味着什么**:以后台服务方式运行、因此停下的矿机,重启之后仍然是停着的,直到下一次预定的复查。
你自己按 Start、或者自己敲 `alice-miner start`,会立刻清除它 —— 自己的矿机自己说了算;只有来自服务
管理器的启动才会尊重那个存下来的停止。

### 12. CPU 引擎会抽 1%,而我们关不掉

我们向打包的 xmrig 传了 `--donate-level 0`。它照样报告 `DONATE 1%`:官方 xmrig 强制 1% 下限,这一点
我们拿本版实际发出去的那个二进制验证过。

也就是说,CPU 矿工大约 1% 的算力去了 xmrig 作者那里,而不是我们的中继 —— 因此也不会变成 ALICE 积分。
它很小,不是新出现的,而且在不更换引擎的前提下我们改不了。我们把它写出来,是因为这件事应该由我们告诉你,
而不是让你在引擎自己的日志里看到一行横幅才知道。

GPU 引擎不受影响。

### 本版不做

**一个双击即开的 macOS App。** 那需要付费 Apple Developer ID 和公证步骤,今天两样都没有;
上面的打包工作不能替代它。

AI 与训练角色调用的外部 Python 引擎,仍然**没有沙箱、继承全部环境变量**。这是真实的设计
缺陷。两个角色**默认关闭**,且 2026-07-21 → 08-04 的服务端日志显示这两个端点总共只有
1 条请求(还是 404),因此**当前暴露为零** —— 但它必须作为独立工程修好,在 AI lane 承载
价值之前,而不是塞进一个客户端批次里。

加密挖矿连接**并未交付**,只交付了客户端这一半。`[CONFIRM-AT-RELEASE]`
